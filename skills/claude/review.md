# /jhw:review — 세션 마무리 리뷰

1. 현재 세션의 대화 내용을 분석하여 다음을 추출한다:
   - 새로운 기술 결정 (Decision Log 후보)
   - AI 사용 피드백/선호도 (Preferences 후보)
   - 프로젝트 상태 변경 (Projects 후보)
   - 새로운 참조 문서 (References 후보)
   - 기술 지식/팁 (Knowledge Base 후보 — `/jhw:note`로 처리)

2. **각 후보별로 `report` 추론** (2단계 — 확실 우선, 추정은 `(추정)` 표시 + 확인):

   ### 2.1 cwd 슬러그 매핑 (확실)
   작업 디렉토리 슬러그 → report 매핑은 `save.md`의 'report 자동 추론' 표를 **단일 소스로 그대로 사용**한다(여기 중복 정의하지 않음 — drift 방지). 슬러그가 명확히 매칭되면 **확정**으로 표시(마커 없음).

   ### 2.2 내용 기반 추정 (cwd 매칭 실패 `etc`/`none`, 또는 후보 도메인이 cwd와 명백히 다를 때)
   후보 본문의 도메인 신호로 report를 **추정**한다. 추정값은 표의 report 옆에 **`(추정)`**을 붙이고, **저장 전 사용자 확인 필수** (워크스페이스 "report 임의 매핑 금지" 규칙 — 임의 채택 금지).

   | 본문 도메인 신호 | 추정 report |
   |---|---|
   | gstApp / 녹화 / mux / RTSP / parser.cpp | pim-app |
   | 카메라 드라이버 / max9296 / AP1302 / AR0234 / edgeconf VHL_CAM / ISP / GMSL | pim-driver-cam |
   | SPI / sc16is7xx | pim-driver-spi |
   | pim-check / 검증 자동화 / setup.py / verify_retry / chk_cam_operate | pim-test |
   | mlan / moal / mcstiercfg / wbridge / L2 bridge / wlan 드라이버 | wlan-driver |
   | pcap / tshark / 802.11 캡처 / RTT / decrypt | wlan-test |
   | Yocto / iMX BSP / DTS / 커널 빌드 (wlan 계열) | wlan-bsp |
   | Notion / 스킬 / MCP / 도구 / 환경 설정 | etc |

   ### 2.3 추정 규칙
   - 도메인 신호가 약하거나 **둘 이상 충돌**하면 추정하지 말고 **빈 값**으로 둔다 (보수적).
   - 추정은 후보 제시일 뿐 — 사용자가 표에서 확정/수정한다. 확정(2.1)과 `(추정)`(2.2)을 표에서 구분 표시.
   - cwd 슬러그 매핑이 명확하면(2.1) 그게 우선. 단 cwd와 후보 본문 도메인이 명백히 다르면 `(추정)`을 같이 제시해 사용자가 고를 수 있게 한다.

3. **자동 중복 제거·합치기 + 저장가치 평가** (사용자 표시 전):
   추출된 후보들을 다음 규칙으로 정리(중복 제거·합치기)하고, 최종 후보 각각의 저장가치를 평가한 뒤 4번 표를 만든다.

   ### 3.1 합치기 적용 조건 (모두 충족 시)
   - 같은 DB (다른 DB는 **절대 합치지 않음**).
   - 같은 도메인/스코프 (같은 파일/모듈/feature, 또는 같은 한 줄 요약으로 묶을 수 있는 주제).
   - 합쳤을 때 검색 시 함께 찾는 게 자연스럽고, 항목 하나로도 의미가 명확함.

   ### 3.2 합치기 패턴 예시
   - 같은 파일에 대한 "신규 작성"과 "후속 보강"의 References 두 항목 → 하나로.
   - 같은 모듈의 여러 키 의미 정정(예: `event_storage_size` 정정 + `id` 정정) → "비채널 키 의미 정정" 하나로.
   - 같은 채널 설정의 AWB / led_flash / 하드웨어 매핑처럼 운영자가 같이 보는 정보 → "채널 설정 종합" 하나로.

   ### 3.3 분리 유지 조건 (의심스러우면 분리)
   - 다른 DB.
   - 같은 DB라도 도메인이 멀거나 검색 시 따로 찾을 가능성이 큼 (예: ISP AWB 매핑과 일반 키 정정).
   - 합치면 본문이 너무 커지거나 한 항목 안에서 주제가 흐려짐.
   - 본문이 jhw_note의 paragraph 한도(2000자)에 근접 — 합치면 초과할 가능성이 있음.

   ### 3.4 합치기 결과 표시
   - 합친 항목의 제목은 통합 제목 (예: "edgeconf 카메라 채널 설정 종합 (AWB / led_flash / 하드웨어)").
   - 본문은 원본 항목들의 섹션 묶음.
   - 표에서 합쳐진 항목은 `(통합 N개)` 표시.

   ### 3.5 paragraph 분할 자동화 (jhw_note 2000자 한도)

   `jhw_note`의 본문은 Notion paragraph 블록 한 개의 한도(**2000자**)에 걸린다. 한도를 넘으면
   API가 `body.children[0].paragraph.rich_text[0].text.content.length should be ≤ 2000`로 거절한다.
   합치기 단계에서 본문을 작성·확정하기 전에 다음 가드를 적용한다.

   > **이 §3.5가 paragraph 분할 룰의 단일 정본이다** (save/project/compact/match는 여기를 참조).
   > `jhw_record`/`jhw_note`는 MCP 레이어(`blocks.ts`)에서 2000자 초과 paragraph를 **자동 분할**하므로
   > 길이 초과로 API가 실패하지는 않는다 — 아래 사전 가드는 분할 품질(가독성·의미 경계)을 위한 것이다.
   > 단, `jhw_start`/`jhw_close`(project 스킬)는 본문을 단일 rich_text로 넣어 자동 분할이 없고
   > `\n\n`로 나눠도 한도를 못 피하므로(한도는 rich_text 객체 1개 길이에 적용), 그 경로에서는
   > 각 본문 필드를 2000자(안전 1800자) 이하로 유지해야 한다.

   #### 3.5.1 작성 규칙 (본문 markdown)
   - 빈 줄(`\n\n`)이 paragraph 분리자다. 모든 `##`/`###` 헤딩 위·아래는 빈 줄로 구분.
   - 한 paragraph(빈 줄 사이의 연속 텍스트 블록)는 **1800자 이하**로 유지 (안전 마진 200자).
   - 코드 블록 ```` ``` ```` 자체도 한 paragraph로 셈. 코드가 길면 의미적 경계(함수, 단계)로 쪼개고 사이에 빈 줄을 둔다.
   - 표(markdown table)도 한 paragraph로 셈. 행 30개를 넘으면 카테고리별로 표를 분할한다.
   - 목록(`-`/`1.`)은 항목 사이에 빈 줄이 없으면 한 paragraph로 합쳐질 수 있으니, 목록이 길면 sub-heading으로 그룹화한 뒤 그룹 사이에 빈 줄을 둔다.

   #### 3.5.2 호출 직전 자동 검증
   `jhw_note`를 호출하기 전, 본문 markdown을 다음 절차로 점검한다:
   1. 본문을 `\n\n`로 split해 paragraph 배열을 만든다.
   2. 각 paragraph의 길이를 센다. 코드 블록은 펜스 포함해서 그대로 길이 계산.
   3. 1800자 초과 paragraph가 있으면 자동 분할 시도 (§3.5.3).
   4. 자동 분할로도 모든 paragraph가 1800자 이하가 되지 않으면 합치기 자체를 포기하고 §3.3 분리 유지로 fallback.

   #### 3.5.3 자동 분할 전략 (우선순위 순)
   1. **sub-heading 추가**: 긴 paragraph 안에 자연스러운 소주제 경계가 있으면 `### 소제목` + `\n\n`을 삽입.
   2. **목록 분할**: 한 paragraph로 합쳐진 긴 bullet 목록은 그룹별로 sub-heading + 빈 줄로 분리.
   3. **코드 블록 분할**: 긴 코드 블록은 의미 단위(함수, 단계, 섹션)로 펜스를 닫고 빈 줄 + 짧은 설명 + 새 펜스로 분리.
   4. **표 분할**: 긴 표는 카테고리별 두 표로 나누고 사이에 빈 줄.
   5. **자연 경계 빈 줄 삽입**: 위 방법으로도 안 되면 마침표(`. `), 세미콜론(`; `), 항목 끝 같은 자연 경계에 빈 줄을 삽입.
   6. 그래도 1800자를 넘는 단일 단위(예: 분할 불가능한 인용 블록)면 그 항목은 합치기를 포기하고 분리.

   #### 3.5.4 회복 로직 (호출이 실패한 경우)
   `jhw_note` 호출이 길이 초과로 실패하면 같은 응답 안에서:
   1. 에러 메시지의 `was N` 값으로 어느 paragraph가 초과했는지 확인.
   2. §3.5.3을 한 단계 더 강하게 적용해 본문을 단축하거나 추가 분할.
   3. 재호출. 두 번째 실패면 합치기를 풀고 원본 항목들로 분리해 다시 시도.

   #### 3.5.5 사전 카운터 표시
   §4 카드의 "통합 N개" 옆에 본문 paragraph 최대 길이를 같이 표시하면 디버깅이 쉽다 (선택):
   ```
   [1] ✅ Knowledge Base  ·  pim-driver-cam  ·  가치=상
       제목: edgeconf 채널 설정 종합 (통합 3개, max 1640자)
   ```

   ### 3.6 저장가치 평가

   합치기까지 끝난 **최종 후보 각각**에 대해 저장가치를 평가한다.
   결과는 §4 표의 `가치`(상/중/하)와 `근거`(한 줄) 컬럼으로 노출한다.

   #### 3.6.1 평가 기준
   - **재사용성**: 다른 세션·작업에서 다시 꺼내 쓸 가능성이 있는가.
   - **검색가치**: 나중에 키워드로 검색해서 찾을 만한 정보인가.
   - **비자명성**: 코드·git 로그·CLAUDE.md·기존 문서에서 다시 유추 가능한 정보는 가치가 낮다.
   - **지속성**: 이번 대화에서만 의미 있는 일시적 맥락이 아니라 두고두고 의미가 있는가.
   - **중복**: 이미 Notion에 저장된 항목과 겹치면 가치가 낮다 (의심되면 `/jhw:recall`로 확인).

   #### 3.6.2 등급 매핑
   - **상**: 재사용 빈번 + 비자명 + 지속적. 저장 강력 권장.
   - **중**: 참고용·검색가치 보통. 저장 권장하나 필수는 아님.
   - **하**: 코드/git에서 유추 가능, 일시적 맥락, 기존 항목과 중복, 또는 너무 사소함.

   `근거`는 **한 줄**로 왜 그 등급인지 적는다 (예: "재사용 빈번·코드서 유추불가", "이미 저장된 선호와 중복").

   #### 3.6.3 기본 저장 여부 (옵트인)
   - **상 / 중 → 저장? 기본 `✅`**.
   - **하 → 저장? 기본 `❌`** (옵트인). 사용자가 "N번 저장"으로 명시해야 켜진다.
   - 즉, 사용자가 그냥 "OK"하면 **상·중만 저장**되고 하 등급은 제외된다. 하까지 저장하려면 "전체 저장".

4. 정리된 항목을 **세로 카드형**으로 보여준다 (한 항목 = 한 카드, `#`/DB/report/가치 메타는 한 줄, 제목·근거는 줄바꿈 허용).
   - 표(markdown table) 사용 금지 — 컬럼 폭 배분이 무너져 가독성이 떨어진다.
   - 각 카드는 빈 줄로 구분한다.
   - 메타 줄 형식: `[N] <저장?이모지> <DB>  ·  <report>  ·  가치=<등급>`
   - 제목·근거 줄은 `    제목: ...` / `    근거: ...`로 들여쓴다 (4 spaces).
   - 마지막에 합치기/등급 요약 + 명령 안내를 둔다.

   예시:
   ```
   📋 세션 리뷰 — Notion 저장 후보 (중복/합치기 + 저장가치 평가 적용 후)

   [1] ✅ Knowledge Base  ·  pim-driver-cam  ·  가치=상
       제목: edgeconf 채널 설정 종합 (통합 3개)
       근거: 재사용 빈번·코드서 유추불가

   [2] ✅ Knowledge Base  ·  pim-app (추정)  ·  가치=중
       제목: raw socket 송수신 키 정정
       근거: 참고용, 검색가치 보통

   [3] ✅ References  ·  pim-driver-cam  ·  가치=중
       제목: 설정 가이드 + release note 보강
       근거: 참고용, 검색가치 보통

   [4] ❌ Preferences  ·  etc  ·  가치=하
       제목: 문서 스타일 — 운영자용 요약 선호
       근거: 이미 저장된 선호와 중복

   ───────────────────────────────────────────────
   원본 N개 → 통합 후 M개 (합치기 K건) · 가치 상 a / 중 b / 하 c
   report: 확정(마커없음) / (추정)=내용 기반, 확인 필요 / 빈칸=신호 약함, 보충 요망
   기본 저장 대상: 상·중 (하는 옵트인) → "OK"하면 ✅ 항목만 저장

   전체 저장? 또는:
     - 낮은 항목 켜기: "4번 저장" (하 등급 옵트인 → ✅)
     - 하까지 전부: "전체 저장" (하 등급 포함)
     - 가치 등급 조정: "4번 가치=상" → 저장? 자동 갱신(상·중→✅)
     - 번호로 제외: "2번 빼"
     - report 변경/확정: "3번 report=wlan-bsp" (추정 확정도 동일: "2번 report=pim-app")
     - 추정 일괄 수락: "추정 OK" → 모든 `(추정)` report를 확정으로
     - 합치기 되돌리기: "1번 분리해" → 합쳐진 원본 항목들 다시 분리
     - 취소: "취소"
   ```

5. 사용자가 승인/수정한다:
   - "OK" → **저장? `✅`인 항목만** 저장 (기본: 상·중). 하 등급은 제외.
   - "전체 저장" → 하 등급까지 **전부** 저장
   - "4번 저장" → 하 등급 4번을 옵트인(저장? `✅`)으로 켜고 저장
   - "4번 가치=상" → 4번 가치 등급 조정 → 저장? 자동 갱신(상·중→✅) 후 저장
   - "2번 빼" → 2번 제외하고 저장
   - "3번 report=wlan-bsp" → 3번의 report 변경/확정 후 저장
   - "추정 OK" → 모든 `(추정)` report를 그대로 확정 후 저장
   - "1번 분리해" → 1번에 합쳐진 원본 항목들을 다시 별도 항목으로 풀어 표 갱신 후 재승인 요청
   - "취소" → 저장 안 함

   **`(추정)` report가 남아 있으면 그냥 "OK"로 넘기지 말고**, 저장 직전 "2번 report 추정 pim-app — 맞나요?"로 한 번 더 확인한다 (임의 채택 금지). 사용자가 확정/수정한 뒤 저장.

6. 승인된 항목마다 `jhw_record` (또는 `jhw_note`) MCP 도구를 호출한다.
   - `properties.report`는 반드시 포함한다.
   - **본문이 있는 항목은 `content` 파라미터로 함께 저장한다** (3.5의 paragraph 가드를 적용한 markdown).
     preferences/projects/references/decisionLog 모두 `jhw_record.content` 지원.
     knowledgeBase는 `jhw_note.content` 사용.
     별도 `notion-update-page` 호출은 불필요.

7. 저장 결과 요약을 보여준다 (저장 N개 / 옵트인 제외된 하 등급 M개 명시).

## 사용 시점

- 세션 종료 전
- 긴 작업 구간이 끝났을 때
- 사용자가 "기록할 거 있어?" 라고 물었을 때

## 규칙

- 저장 후보가 없으면 "이번 세션에서 저장할 항목이 없습니다"로 응답한다.
- 실패한 시도나 중간 과정은 후보에서 제외한다.
- 이미 저장된 항목은 중복 제안하지 않는다.
- **저장가치 평가는 합치기 후 최종 후보에 적용**한다. 기준: 재사용성·검색가치·비자명성·지속성·중복 (§3.6).
- **가치 '하'는 기본 제외(❌) 옵트인.** "OK"는 상·중만 저장, "전체 저장"은 하 포함, "N번 저장"은 특정 하 항목만 켠다.
- **`report`는 2단계 추론**(§2): cwd 슬러그 매핑(확실) → 실패 시 본문 도메인 기반 추정(`(추정)` 표시). 신호 약하거나 충돌하면 빈 값.
- **추정 report는 임의 채택 금지** — 저장 전 사용자 확인 필수("report 임의 매핑 금지" 규칙). 확정/`(추정)`/빈칸을 표에서 구분.
- 보고서에 노출 원치 않는 항목은 `report=none`으로 명시 (보고 제외).
